# US-002 Test Cases — Vote on Stories

**Story:** `docs/requirements/US-002-vote-on-stories.md`  
**Dev spec:** `docs/specs/US-002-dev-spec.md`  
**Date:** 2026-10-08  
**Status:** Draft — pending confirmation of the sender-identity limitation noted below

## Test design

- **Scope:** Functional, integration, accessibility, and focused security coverage for AC-1–AC-10 and the development spec.
- **Risk focus:** Host authority, pre-Reveal Vote privacy, Round transitions, Broadcast integration, and loss or reordering of messages.
- **Techniques:** State Transition Testing for Phase changes; Decision Table Testing for Host/Guest permissions; Equivalence Partitioning for Card values and Story titles; Use Case Testing for multi-Participant flows; Error Guessing for malformed payloads and XSS.
- **Level:** Unit cases target pure functions, message guards, and storage; E2E cases use Playwright against the Supabase Realtime project with each Participant in a separate browser context.
- **Automation:** All listed cases are suitable for automation. E2E cases require the configured Supabase Realtime environment.
- **Out of scope:** Average and other calculated Results belong to US-003; no tests for those calculations are included.

## Conventions

- Test names include `US-002` and the `TC-002-NN` ID.
- E2E setup uses Browser A for the Host and separate fresh browser contexts for each Guest. Every test creates its own Room; read the generated Room code from `room-code-value`.
- Host E2E setup waits for `room-view` using the configured Playwright timeout. Broadcast synchronization is asserted by waiting for the expected state condition; US-002 defines no additional timing threshold. Do not use fixed sleeps unless elapsed time itself is under test.
- Use the `data-testid` values defined in section 6 of the development spec. For the “own Vote” expectation, the Guest must inspect only its local UI; capture the received `room:state` payload separately to verify that no Vote value crossed the channel before Reveal.
- Unit test titles follow `US-002 TC-002-NN <description>`.
- In the test steps, “Host snapshot” means the value stored under `story-app:host-room`.

## Risks, assumptions, and exclusions

- **Sender identity:** The existing Broadcast contract supplies a `participantId` but does not authenticate the sender cryptographically. TC-002-13 verifies that a registered Guest ID cannot authorize Host-only actions at the Reducer boundary. Impersonating the Host's ID is not asserted as preventable by these cases; the development spec records this limitation as an open question.
- **Timing:** No US-002-specific synchronization threshold is defined. E2E cases wait for observable state rather than asserting an invented deadline.
- **Accessibility:** The story does not specify a full accessibility standard. TC-002-23 checks keyboard operability and accessible names for interactive controls as a focused baseline.
- **Security:** TC-002-24 verifies that unrestricted title text is safely rendered. It does not impose new Story-title validation rules.
- **Results:** Average, most common, highest, lowest, and Consensus are excluded because they belong to US-003.
